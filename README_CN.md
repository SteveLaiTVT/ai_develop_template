# AI 辅助开发模板

一个结构化的工作流模板，用于与多模型 AI 进行结对编程构建应用程序。采用多会话架构，AI 在不同上下文中分别处理设计、实现和审查工作。

**[English](README.md)**

## 这是什么

一个**项目脚手架和工作流系统**，适合想要：

- 借助 AI 辅助构建全栈应用
- 通过结构化 AI 协作维护代码质量
- 保持 AI 上下文聚焦和可管理
- 从个人开发扩展到团队协作
- 使用 OpenSpec 进行规范驱动开发

## 核心功能

| 功能 | 描述 |
|------|------|
| **三会话模型** | A（架构师）→ B（实现者）→ C（审查者）|
| **需求发现框架** | A 会话在设计前先访谈用户 |
| **状态提示系统** | 所有会话启动时显示工作流状态 |
| **自测试工作流** | B 会话像真正的开发者一样运行服务器和测试 |
| **MCP/Agent 测试集成** | 前端可视化测试优先使用 MCP/Agent 浏览器工具 |
| **PR 与缺陷修复模式** | B 会话创建 PR，然后修复问题直到通过审批 |
| **OpenSpec 集成** | 基于详细规范的规范驱动开发 |
| **模型无关** | A/B/C 会话可由不同模型承担，职责独立于具体厂商 |

### 三会话模型

| 会话 | 模型 | 角色 | 职责 |
|------|------|------|------|
| **A** | 强推理模型 | 架构师 | 需求发现访谈、架构设计、带 TODO 的骨架代码、定义友好异常提示 |
| **B** | 高效执行模型 | 实现者 | 填充 TODO、自测试（含异常数据）、创建 PR、修复缺陷模式 |
| **C** | 审查模型 | 审查者 | 验证约束、发现问题、批准 PR |

## 新功能详解

### 1. 需求发现框架（A 会话）

在设计之前，A 会话会进行**需求发现访谈**以了解：

```
📱 谁会使用这个应用？
   • 年龄范围、技术水平、无障碍需求

🔧 你的技术背景
   • 前端/后端经验、现有资源

🎯 你的产品愿景
   • 核心问题、MVP 范围、设计风格

⚠️ 约束条件
   • 预算、合规要求、集成需求
```

结果存储在 DESIGN_STATE.yaml 的 `discovery` 部分。

### 2. 状态提示系统（所有会话）

每个会话启动时都会显示**工作流状态**：

```
╔══════════════════════════════════════════════════════════════════╗
║                    🚀 AI 开发工作流                               ║
╠══════════════════════════════════════════════════════════════════╣
║ 当前阶段: implementation（实现中）                                ║
║ 项目: 我的应用                                                   ║
╠══════════════════════════════════════════════════════════════════╣
║ 会话状态                                                         ║
║ ┌────────────┬────────────┬────────────┐                        ║
║ │  A 会话    │  B 会话    │  C 会话    │                        ║
║ │  等待中    │ ▶ 活跃     │  待处理    │                        ║
║ └────────────┴────────────┴────────────┘                        ║
╠══════════════════════════════════════════════════════════════════╣
║ 👉 下一步: B 会话应该实现代码并进行自测试                          ║
╚══════════════════════════════════════════════════════════════════╝
```

### 3. B 会话自测试工作流

B 会话像**真正的开发者**一样工作：

```
┌─────────────────────────────────────────────────────────────────┐
│              完整的 B 会话工作流                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  阶段 0: 显示状态提示                                             │
│     ↓                                                            │
│  阶段 1: 环境检查（如缺少环境变量则暂停）                          │
│     ↓                                                            │
│  填充 TODO + 提交 WIP                                            │
│     ↓                                                            │
│  阶段 2: 后端自测试（启动服务器、测试 API）                        │
│     ↓                                                            │
│  阶段 3: 前端自测试（MCP/Agent）[优先]                           │
│     ↓                                                            │
│  阶段 4: 提交可工作的代码                                         │
│     ↓                                                            │
│  阶段 5: 创建 Pull Request                                       │
│     ↓                                                            │
│  阶段 6: 缺陷修复模式 ◄─────────────────────┐                     │
│     ↓    （等待反馈）                       │                     │
│  修复问题 → 自测试 → 推送 ──────────────────┘                     │
│     ↓                        （重复直到通过审批）                  │
│  PR 批准并合并 → 任务完成                                         │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 4. 环境变量暂停行为

如果 B 会话需要环境变量才能运行：

```
╔══════════════════════════════════════════════════════════════════╗
║  ⚠️  缺少环境变量 - 需要操作                                      ║
╠══════════════════════════════════════════════════════════════════╣
║                                                                  ║
║  变量: DATABASE_URL                                              ║
║  用途: PostgreSQL 数据库连接                                      ║
║  示例: postgresql://user:password@localhost:5432/mydb            ║
║                                                                  ║
║  请将此变量添加到 .env 文件中。                                   ║
║  完成后回复 "ready"。                                            ║
║                                                                  ║
╚══════════════════════════════════════════════════════════════════╝

⏸️ 已暂停 - 等待用户配置环境
```

### 5. MCP/Agent 测试集成（强制优先）

**MCP (Model Context Protocol，模型上下文协议)** 是一种标准协议，允许 AI 助手与外部工具和服务交互，包括用于测试的浏览器自动化。

对于有前端的项目（`project_analysis.has_frontend: true`），B 会话应优先使用 MCP 兼容的浏览器工具进行可视化测试:

- 导航到页面
- 用模拟数据填写表单
- 点击按钮并验证响应
- 测试响应式设计（手机/平板/桌面）

**推荐工具：**
- **Playwright MCP Server** - 浏览器自动化测试
- 其他 MCP 兼容的浏览器代理

**后备方案：** 如 MCP 不可用，需明确记录限制并请求用户手动验证

### 6. PR 创建与缺陷修复模式

自测试通过后，B 会话会：
1. **创建 PR** - 包含详细描述和自测试结果
2. **进入缺陷修复模式** - 等待 C 会话审查和用户反馈
3. **修复问题** → 重新自测试 → 推送到 PR
4. **重复** 直到 PR 被批准并合并

## 技术选型与维护策略

本模板不强制任何前端/后端/移动技术栈。流程要求：

1. **尊重用户偏好**：用户给出技术选型时，按其选型执行。
2. **可推荐但不强制**：若用户要求推荐，A 会话给出 1-2 个可行方案并说明理由。
3. **使用最新稳定版本**：优先选择稳定/长期支持版本，并遵循官方最佳实践。
4. **维护 AGENTS.md/AGENT.md**：在各模块目录维护 AGENTS.md/AGENT.md 以便其他模型协作与交接。

## 快速开始

### 1. 克隆和设置

```bash
git clone https://github.com/yourusername/ai-develop-template.git my-project
cd my-project
pnpm install
```

### 2. 自定义 DESIGN_STATE.yaml

编辑 `.claude/DESIGN_STATE.yaml` 填入你的项目详情。

### 3. 安装 OpenSpec（可选）

```bash
npm install -g @fission-ai/openspec@latest
```

### 4. 开始第一次迭代

**A 会话（强推理模型）：**
1. 打开新的 AI 助手对话
2. 粘贴 `.claude/prompts/A_SESSION.md` 的内容
3. A 会话显示状态提示，进行需求发现访谈
4. 创建带 TODO 的骨架代码

**B 会话（高效执行模型）：**
1. 打开新对话
2. 粘贴 `.claude/prompts/B_SESSION.md` 的内容
3. B 会话显示状态提示，填充 TODO
4. 运行自测试（后端 API、前端可视化）
5. 创建 PR，进入缺陷修复模式

**C 会话（审查模型）：**
1. 打开新对话
2. 粘贴 `.claude/prompts/C_SESSION.md` 的内容
3. 根据约束条件审查代码
4. 批准或请求修改

## 核心原则

### 1. 单一事实来源
只有 `DESIGN_STATE.yaml` 定义项目。

### 2. 角色分离
- A 会话：只做决策，不实现
- B 会话：只实现，不改设计
- C 会话：只审查，不改代码

### 3. 类人工作流
B 会话像真正的开发者一样工作：
- 写代码 → 启动服务器 → 测试 → 修复 → 提交可工作的代码

### 4. 环境安全
B 会话在缺少环境变量时会暂停并询问用户。

### 5. 迭代修复
修复 → 自测试 → 推送 → 重复直到通过。

## 部署要求

在涉及前后端的功能交付时：

1. **最低要求**：提供 Docker 部署说明（Dockerfile/compose）。
2. **优先方案**：如有 Web 前端，提供 Vercel 部署说明。
3. **环境变量**：明确列出各运行环境所需的变量（本地/Docker/Vercel）。
4. **代码审查**：合并前确认部署说明与环境变量清单已完整。
